# Interview Talking Points

- **Why the VM tier uses kubeadm instead of k3s, EKS Anywhere, or a managed alternative:** it deliberately reproduces the real operational burden (you own upgrades, the CNI, the control plane) rather than abstracting it away — k3s bundles away enough of that (embedded etcd, a baked-in CNI) that it would under-demonstrate the skill a hybrid-fleet role screens for.
- **Why the VM-tier nodes are SSM-only, with the kubeadm bootstrap itself run over Ansible's `aws_ssm` connection plugin:** no SSH key ever exists for this tier, not even one that's merely unused — the security group has zero inbound rules, full stop. Every bootstrap action is in the Session Manager audit log for free.
- **Why Nexus lives on a VM, not in a container on EKS:** matches the real target environment and demonstrates comfort operating stateful infra outside of Kubernetes, including backup/restore discipline.
- **Why Nexus's EBS data volume is provisioned separately from the instance, with `prevent_destroy`:** the rest of this repo treats compute as disposable (an ASG replaces a bad node, config re-applies); Nexus is the deliberate exception — its blob store has to outlive any single instance, so the volume's lifecycle is structurally decoupled from the instance's, not just backed up and hoped for.
- **Why ARC runners are ephemeral rather than a static pool:** security (no persistent lateral-movement surface) and cost (no idle capacity) — a single decision that improves both.
- **Why OpenTelemetry over a single vendor agent:** keeps the observability backend swappable, directly answering the "familiarity with Datadog/Grafana/OTel/ELK" ask as interchangeable rather than a single bet.
- **Cost-allocation tagging per team, as two real mechanisms at two layers, not one:** the AWS-resource side (`terraform/modules/cost-allocation-tags` activating `Project`/`Environment`/`Tier`/`CostCenter` via `aws_ce_cost_allocation_tag`) and the K8s-workload side (`require-team-label.yaml`'s enforced `team` label, bridged into Cost Explorer/CUR by AWS's real Split Cost Allocation Data for EKS feature). An extension of a finance/accounting background — chargeback and auditability translate directly into platform engineering discipline.
- **The cost-allocation-tag activation delay is a real AWS eventual-consistency constraint, not an oversight:** AWS won't activate a tag for cost allocation until it's been applied to a resource for ~24h, which is why `terraform/live/global/cost-allocation-tags` is documented and sequenced to apply *last*, not bundled into the stacks that create the tagged resources in the first place. A small, concrete example of infra-as-code needing to model a real-world ordering constraint, not just resource dependencies Terraform already understands.
- **The on-call runbook's alert-to-response mapping is read directly off the alarm/rule definitions, not written from memory:** `docs/runbooks/on-call-triage.md`'s alarm names, thresholds, and metric dimensions were pulled from `terraform/modules/observability/main.tf` itself — the same "verify, don't assume" discipline applied to a doc as to code.
- **Why EKS and Karpenter are separate Terragrunt stacks, not one:** avoids the classic "Helm/Kubernetes provider configured from a resource created in the same apply" chicken-and-egg problem — see [`docs/architecture.md`](architecture.md#why-eks-and-karpenter-are-separate-terragrunt-stacks). A small detail that signals real hands-on Terraform experience rather than copy-pasted examples.
- **Why the Site-to-Site VPN is a real tunnel (VGW + self-managed strongSwan), not just a diagram box:** both VPCs being in the same AWS account doesn't mean the link between them has to be fake — a Customer Gateway needs *some* real IP to terminate at, and a small EC2 instance playing that role is a legitimate, common way to simulate a DC interconnect in a portfolio/lab context.
- **The `for_each`-over-unknown-values gotcha caught while building the VPN module:** security-group rules meant to scope inbound IKE/NAT-T to AWS's own tunnel endpoint IPs can't use `for_each` over those addresses, because `for_each`'s key set must be known at plan time and the addresses aren't known until the VPN connection is actually created — fixed with four singleton resources instead. A concrete example of a correctness bug that only shows up on a first real apply, not in `terraform validate`.
- **Fetching the ALB controller's IAM policy from its own GitHub release at apply time, instead of hand-copying a ~200-line JSON policy:** the policy changes as AWS adds ALB/NLB features, and a stale or subtly wrong hand-transcribed copy fails silently as a runtime `AccessDenied` on one specific action — not as a Terraform error you'd catch early.
- **Why "policy parity" between the two clusters is a literal, checkable claim, not an architecture-diagram aspiration:** the Gatekeeper *controller* has to be installed differently per tier (Terraform+helm on EKS, Ansible+helm over SSM on the VM tier — there's no Terraform-managed K8s layer on that side to attach a `helm_release` to), but the actual policy content — `ConstraintTemplate`s and `Constraint`s — is `kubectl apply`-ed with the exact same command against both clusters' kubeconfigs. Same files, same command, twice.
- **Validating Rego policy logic without a live cluster:** installed the `opa` CLI and ran `opa check` + `opa eval` with both violating and passing sample inputs against each `ConstraintTemplate`'s extracted Rego — caught that OPA's own CLI defaults to v1 syntax (requiring `if`/`contains` keywords) since OPA 1.0, while Gatekeeper 3.17.1's bundled engine predates that and expects the older syntax; `--v0-compatible` is what actually matches what Gatekeeper runs. The kind of version-compatibility detail that's easy to get wrong writing Rego from memory and easy to catch by actually running it.
- **The OTel Collector's pipeline config is one file, rendered two ways, verified to produce identical output:** Terraform's `templatefile()` on EKS, Ansible's Jinja `replace` filter over the raw file on the VM tier (that tier's `sigv4auth` extension authenticates via the instance's own IMDS-sourced IAM role, since there's no OIDC provider to attach IRSA to) — actually diffed both renders against the same two substituted values before committing, rather than assuming two different templating engines would agree.
- **Why CloudWatch alarms route to PagerDuty/OpsGenie via SNS, not through Amazon Managed Prometheus's Alertmanager:** the brief's shorthand reads like one pipeline, but AMP's Alertmanager only ever receives alerts Prometheus itself evaluated — there's no AWS-native bridge feeding CloudWatch alarm state into it. Two parallel paths to the same destination, not the single pipeline the arrow suggests; worth catching before building something that silently can't work as literally diagrammed.
- **The module registry isn't documented aspiration — every stack actually consumes its module by git tag:** `cloud-vpc` and `onprem-vpc` both pull the identical `modules/vpc/v1.0.0`, proving cross-tier module reuse rather than asserting it. The fetch mechanism (git tag + `//subdirectory`, plus a module's relative reference to a sibling module like `karpenter → ../iam-irsa`) was verified against a real tag/fetch round-trip before wiring all thirteen stacks to it, not assumed from the URL syntax being plausible.
- **Applying Terragrunt's `_envcommon` pattern to cross-controller duplication, not the textbook cross-environment case:** the pattern is normally shown solving "same component repeated across dev/staging/prod"; this repo has one environment, so what's actually being deduplicated is five EKS-controller stacks' identical `helm` provider boilerplate. Same shared-include mechanism, honestly labeled as solving a different problem than the one it's usually demonstrated for.

## Internal Reuse Notes

- Reuses the EKS + Karpenter pattern already established elsewhere — no need to re-justify that choice from scratch in this project.
- The Terraform module registry and Terragrunt pattern is a natural precursor to a companion Terragrunt/CI-CD-focused project — this repo can absorb that scope rather than duplicating it later.
- OPA/Gatekeeper usage here is consistent with a policy-as-code approach used in a developer-platform-focused project; the two can cross-reference each other as the same governance philosophy applied at different layers (developer platform vs. hybrid fleet).
